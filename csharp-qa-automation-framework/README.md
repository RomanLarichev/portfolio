# 🇷🇺 Русская версия

## 🎯 О проекте

**C# QA Automation Framework — Portfolio Edition** — компактная публичная версия более крупного приватного фреймворка автоматизации тестирования на **.NET 8 / Playwright / xUnit**.

Цель репозитория — показать не весь внутренний фреймворк, а наиболее важные архитектурные идеи, полезные при автоматизации крупных и нестабильных web-приложений:

- ранжирование локаторов по надежности;
- определение динамических DOM-id;
- мониторинг «здоровья» селекторов;
- сбор статистики успешности и задержек;
- изолированная browser-инфраструктура;
- unit- и browser-integration тесты;
- CI через GitHub Actions.

Публичная версия не содержит внутренних URL, учетных данных, customer data, production-конфигурации или доменно-специфичного кода.

## ✨ Основные возможности

- **.NET 8**
- **xUnit**
- **Microsoft Playwright**
- ранжирование локаторов: `data-testid` → стабильный `id` → ARIA/name/placeholder → label
- определение GUID/Blazor-подобных динамических `id`
- selector-health telemetry
- расчет success rate и средней latency селектора
- выбор наиболее успешной стратегии поиска
- thread-safe хранилище статистики
- изолированная Playwright browser session
- unit-тесты и browser integration tests
- GitHub Actions CI с Chromium
- только synthetic/demo data

## 💡 Зачем это нужно

В крупных enterprise-приложениях DOM часто меняется, а autogenerated `id` могут быть нестабильными. Если автотест хранит один жестко заданный CSS/XPath-селектор на поле, тесты становятся хрупкими и начинают падать после незначительных изменений интерфейса.

В этой версии показан другой подход:

```text
намерение найти поле
        ↓
набор кандидатов локаторов
        ↓
ранжирование по стабильности
        ↓
попытка найти элемент
        ↓
фиксация результата и latency
        ↓
обновление selector-health статистики
        ↓
возврат рабочего locator
```

Такой подход делает инфраструктуру автотестов устойчивее к изменениям UI и позволяет понимать, какие селекторы становятся проблемными.

## 🔎 Пример использования

```csharp
var store = new SelectorHealthStore();
var health = new SelectorHealthMonitor(store);
var resolver = new RankingLocator(page, health: health);

var email = await resolver.FindBestAsync("email");
await email!.FillAsync("qa@example.test");

var stats = store.GetFieldStats("email");
Console.WriteLine($"Success rate: {stats.SuccessRate:F1}%");
```

# 🇬🇧 English Version

## 🎯 About

**C# QA Automation Framework — Portfolio Edition** is a compact public showcase of a larger private automation framework built with **.NET 8 / Playwright / xUnit**.

The goal of this repository is not to publish the whole private framework. Instead, it demonstrates several architecture ideas that are especially useful for large and unstable web applications:

- ranked locator resolution;
- dynamic DOM id detection;
- selector-health monitoring;
- success-rate and latency tracking;
- isolated browser infrastructure;
- unit and browser integration testing;
- CI with GitHub Actions.

The public edition contains no private URLs, credentials, customer data, production configuration or domain-specific implementation.

## ✨ Highlights

- **.NET 8**
- **xUnit**
- **Microsoft Playwright**
- ranked locator strategy: `data-testid` → stable `id` → ARIA/name/placeholder → label
- GUID/Blazor-like dynamic id detection
- selector-health telemetry
- selector success-rate and latency statistics
- best-strategy selection based on observed results
- thread-safe telemetry storage
- isolated Playwright browser session
- unit tests and browser integration tests
- GitHub Actions CI with Chromium
- synthetic/demo data only

## 💡 Why this exists

Large enterprise web applications often change DOM structure while keeping the same business behavior. Auto-generated ids can also be unstable. A framework that stores one hard-coded CSS or XPath selector per field quickly becomes brittle.

This sample demonstrates a different approach:

```text
field intent
    ↓
ranked locator candidates
    ↓
try the most stable strategy first
    ↓
record result and latency
    ↓
update selector-health statistics
    ↓
return a working locator
```

This approach improves UI-test resilience and provides visibility into selectors that are becoming unreliable.
